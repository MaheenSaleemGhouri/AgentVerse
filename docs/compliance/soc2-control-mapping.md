# SOC 2 Readiness — Control Mapping

**This is a SOC 2 *readiness* self-assessment, not a certification.** AgentVerse has not engaged an auditor and holds no SOC 2 report. Every row below cites a real, checkable mechanism in this repository — a file, a migration, a CI job — never an aspiration stated as fact. Where no such mechanism exists, the row says so as **GAP**, not as a euphemism. This doc is Area 5 of the Phase 12 plan and is written last, after the areas whose evidence it cites (audit-log completeness/immutability, the MCP server surface, dedicated-worker routing, marketplace purchase, multi-region topology) were actually built — never the reverse.

**Status legend:** **IMPLEMENTED** — a real, verified mechanism exists and is exercised by tests or is directly inspectable in code/config. **PARTIALLY IMPLEMENTED** — a real mechanism exists but a stated part of the control is not yet built, or the control depends on something outside this repository (a GitHub org setting, a hosting provider's own SOC 2 report) that cannot be verified from the code alone. **GAP** — no real mechanism exists yet.

| Control area | Status | Evidence | Notes |
|---|---|---|---|
| **Access control (tenant isolation)** | IMPLEMENTED | Every tenant-owned table carries `workspace_id` with a leading index (CLAUDE.md Rule 11, `database-architect`-owned schema); `authorization-expert`'s composite-index convention `(workspace_id, ...)` is used throughout `infrastructure/migrations/versions/`. `get_current_workspace` resolves `workspace_id` from the authenticated identity only, never from client input. | Verified structurally (schema convention), not by an exhaustive per-table audit in this pass — `owasp-expert`'s standing A01 review is the ongoing verification mechanism, not this doc. |
| **Authentication** | IMPLEMENTED | `authentication-expert`'s stack: Better Auth session cookies (`httpOnly`/`Secure`/`SameSite`), OAuth/SSO via `sso_service.py` with real SAML assertion validation (`@node-saml/node-saml`) and OIDC dynamic-provider registration, API keys SHA-256-hashed at rest via `ApiKeyService`. `api_keys.kind` (ADR-0017) separates REST credentials from MCP credentials so a leaked one cannot authenticate the other's surface. | SSO/SCIM confirmed real (not stubbed) by direct code audit in the Phase 12 planning pass — see the plan's "What audits confirmed already exists" section. |
| **Authorization / RBAC** | IMPLEMENTED | Single shared `require_role`/`require_member`/`require_admin`/`require_owner` dependency factory (`auth_service/interface/dependencies/require_role.py`), deny-by-default, audits every denial before returning 403. Workspace roles are a strict hierarchy (`owner > admin > member > viewer`). `require_capability` (ADR-0018) is a separate, explicitly non-security routing decision — documented as such so it is never mistaken for an access-control gate. | |
| **Audit logging** | IMPLEMENTED | `audit_logs` (append-only, `AuditService.record`) is now called from every subsystem's real write paths — auth, RBAC, SSO, SCIM (pre-existing), and as of Phase 12 Area 1: `orchestration_service` (agent/workflow/team lifecycle), `marketplace_service` (submit/publish/unlist/relist/install/review), `billing_service` (plan changes, cancellations), plus the two new auth events `auth.login_failed`/`auth.sso_login`. The Phase 12 MCP server (ADR-0017) and marketplace purchase (Area 2) audit their own actions the same way (`mcp_server.tool_executed`/`tool_denied`, `marketplace.listing_installed` with `payment_intent_id`). | |
| **Audit log immutability** | IMPLEMENTED | Postgres trigger `prevent_audit_log_mutation()`, `BEFORE UPDATE OR DELETE ON audit_logs FOR EACH ROW`, raises on both operations — DB-level, not application-convention-level. Added in Phase 12 Area 1, migration in `infrastructure/migrations/versions/`. | A trigger rather than a role `REVOKE`, deliberately — portable regardless of which DB role the app connects as in a given environment (the plan's explicit scope decision). |
| **Change management** | PARTIALLY IMPLEMENTED | Conventional-commit discipline, `CODEOWNERS` mapping paths to owning roles (`.github/CODEOWNERS`), required CI checks (`.github/workflows/ci.yml`: lint, type-check, unit/integration tests, dependency audit) gating merge. ADRs (`docs/adr/0001`–`0019`) record every architecturally significant decision with context/decision/consequences/alternatives. | **Gap inside this control:** actual GitHub branch-protection-rule enforcement (required reviewers, no direct pushes to `main`) is a repository *setting*, not a file this codebase can assert from the inside — this doc cannot verify it is switched on without querying the GitHub API with admin access, which is out of scope here. |
| **Incident response** | PARTIALLY IMPLEMENTED | Per-service rollback runbooks exist and are concrete (`docs/runbooks/rollback-{api,web,worker}.md`, `docs/runbooks/billing.md`). Structured logging carries `request_id`/`workspace_id`/`run_id` for investigation (CLAUDE.md §7/§12). Alerting infra exists (`infra/observability/alertmanager.yml`, `alerts.yml`). | **Gap:** no single incident-response *policy* document exists — severity definitions, on-call escalation path, communication/disclosure procedure, and postmortem template are not written down anywhere in this repo. The pieces a response would use (runbooks, logs, alerts) are real; the process that ties them together during an actual incident is not documented. |
| **Data protection (in transit)** | IMPLEMENTED | TLS is the platform-wide transport assumption (Vercel for `apps/web`, and every documented deployment target for `apps/api`/`apps/worker`); no code path constructs a plaintext `http://` connection to a production dependency. | Verified as a stated architectural assumption (CLAUDE.md §10), not independently re-audited connection-string-by-connection-string in this pass. |
| **Data protection (at rest)** | PARTIALLY IMPLEMENTED | Application-layer secrets (OAuth tokens, MCP credentials) are sealed via `CredentialVault`/`KeyRing` envelope encryption (`packages/python-shared/.../security/envelope.py`) before they ever reach Postgres — not plaintext at rest regardless of the disk-level posture. | **Gap:** whole-database disk-level encryption at rest is a property of the hosting provider's managed Postgres offering, not something this codebase configures directly — it is not independently verified here, and no deployment target has been confirmed to have it enabled. |
| **Secrets management** | IMPLEMENTED | `Settings` (Pydantic `BaseSettings`) is the sole reader of environment configuration platform-wide (CLAUDE.md §7) — no scattered `os.environ` reads. A missing required secret fails startup loudly; `os.environ.get("KEY", "changeme")`-style fallbacks are prohibited and none exist in the reviewed config modules. `NEXT_PUBLIC_*` variables are the one legitimate client-bundle exception, by convention. | |
| **Vulnerability management** | IMPLEMENTED | `.github/workflows/ci.yml`'s `dependency-audit` job runs `pnpm audit` (JS/TS) and `uvx pip-audit --local` (each Python service) as a required CI check on every PR touching manifests, *and* on a nightly cron (`schedule: cron: "17 3 * * *"`) — both cadences CLAUDE.md §10 requires. | |
| **Monitoring / observability** | IMPLEMENTED | Every service exposes `/health` and `/ready` with correct liveness/readiness semantics (Phase 12 Area 6 added region identification to both). `infra/observability/` holds real Prometheus scrape config, Grafana dashboards, and Alertmanager routing — not placeholders. Structured JSON logging with correlation IDs (`logging-expert`'s standard) is used throughout `apps/api`/`apps/worker`. | |
| **Backup & recovery** | IMPLEMENTED | `infra/backup/{backup,restore,verify}.sh` — `verify.sh` runs backup *and* restore against a scratch database, matching `cloud-architect`'s standing rule that an untested backup is a hypothesis, not a recovery plan. Scope is explicit: Postgres only (the system of record); Redis, Stripe, and object storage are each named with the reason they are excluded (reconstructable, provider-owned, or lifecycle-policy-owned respectively). | |
| **Business continuity** | GAP | No documented RPO/RTO target, no multi-region failover (ADR-0019 states the target topology and explicitly that it is not deployed today), and no tested disaster-recovery drill beyond the backup/restore/verify scripts above (which cover data loss, not service availability during a regional outage). | This is the most substantial open item this mapping surfaces — see the gap register. |
| **Vendor / sub-processor management** | GAP | No vendor register or sub-processor list exists in this repository (Stripe, the LLM providers, the hosting platform, the email/notification provider would all need to be enumerated with their own compliance posture for a real SOC 2 engagement). | |

## What this mapping does not claim

- It does not claim AgentVerse is SOC 2 compliant, certified, or audit-ready in the sense an auditor would sign off on.
- It does not substitute for `owasp-expert`'s standing OWASP Top 10 audit, `security-reviewer`'s per-PR gate, or `security-engineer`'s architectural threat models — this is a compliance-framework mapping over their combined output, not a replacement for any of them.
- Every "IMPLEMENTED" row above is falsifiable by reading the cited file/migration/CI job directly — that is the point of citing real mechanisms rather than describing intent.
