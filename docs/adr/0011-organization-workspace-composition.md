# ADR-0011: Organization/Workspace Composition

## Context

The enterprise workspace/security initiative asks for an Organization → Department → Team → Project hierarchy above the existing `workspaces`/`workspace_members` layer (ADR-0004), plus org-scoped SSO and billing rollup in later increments. `CLAUDE.md` Rule 11 makes `workspace_id` tenant isolation absolute: "every tenant-owned table, every query, every cache key... carries and filters by `workspace_id`; cross-workspace access is denied without leaking existence." The existing `workspace_members` RBAC layer (ADR-0004) is working, tested, and load-bearing for every route in the platform. This ADR decides how a new organization concept composes with that existing layer without weakening or duplicating it.

**The fork:** does "Organization" become a *second*, higher-level isolation root (workspaces live *inside* an organization's authorization boundary, org roles imply workspace access), or does it become an *additive grouping layer* (workspaces stay independently authorized via `workspace_members`; an organization only groups them for billing/SSO/branding, granting no access of its own)? This was raised to and decided by the project owner before implementation began, precisely because it determines whether every subsequent increment is additive or a system-wide re-architecture.

## Decision

**Organization is an additive, non-isolating grouping layer. `workspace_id` remains the only real tenant-isolation boundary.**

- `organizations` and `organization_members` are new tables, structurally parallel to `workspaces`/`workspace_members` (same four-role hierarchy, reusing the existing `workspace_role` Postgres ENUM type rather than defining a second one — DRY, `CLAUDE.md` §16).
- `workspaces.organization_id` is a **nullable** foreign key, `ON DELETE SET NULL`. One organization groups N workspaces; a workspace belongs to at most one organization at a time (not an M:N link table — an M:N model would leave "which org's SSO/billing config applies to this workspace" genuinely ambiguous, a real problem this platform does not need to solve).
- **The core invariant: attaching a workspace to an organization grants zero implicit workspace access.** `workspace_members` is never read, written, or reasoned about by any organization-service code path. Even an organization's sole owner has no access to a workspace attached to that organization without their own separate `workspace_members` row. `get_current_organization`/`require_org_role` are structurally identical to, but fully independent of, `get_current_workspace`/`require_role` — two parallel dependency chains that are never merged into one.
- **Attach/detach requires proving control of both sides.** The attach/detach routes compose two independently resolved contexts in one handler: `require_org_role(Role.ADMIN)` on the organization *and* `require_owner` (existing workspace dependency) on the target workspace. An org admin cannot attach a workspace they do not own; a workspace owner cannot be forced into an organization by that organization's admin alone.
- **Deleting an organization detaches, never deletes, its workspaces.** `ON DELETE SET NULL` at the database level does this automatically — no application-layer "detach all workspaces then delete" step exists or is needed, and none should be added (a manual detach loop would be redundant with the FK constraint and a place a future edit could introduce a bug the constraint already prevents).
- `audit_logs.organization_id` is a new nullable column (also `ON DELETE SET NULL`) for organization-level events (`organization.created`, `organization_member.role_changed`, etc.) that have no single workspace to attribute to — parallel to the existing nullable `audit_logs.workspace_id`.

## Consequences

**Positive:** every increment building on organizations (SSO config, billing rollup, branding) is additive — it reads `organizations`/`organization_members` and never has to reason about, or risk weakening, the existing workspace RBAC that every other route in the platform already depends on. The two authorization dependency chains can be reasoned about, tested, and audited completely independently. A bug in organization-membership logic cannot, by construction, grant or revoke workspace access, because no code path connects the two.

**Negative:** an admin who wants "everyone in this org can see every workspace in it" does not get that automatically — it requires explicit workspace invitations per workspace, same as today. This is treated as correct, not a gap: implicit cross-workspace access from org membership alone is exactly the kind of authorization shortcut Rule 11 exists to prevent, and the initiative's own spec does not ask for it. If a future requirement genuinely needs org-wide workspace visibility, it is a new, explicit feature (e.g., an opt-in "org admins can request access" flow with its own audit trail) — not a silent default.

## Alternatives considered

- **Organization as a second isolation root** (workspaces scoped inside an org's authorization boundary; org role implies workspace role). Rejected: would require every existing workspace-scoped route, query, and cache key to also reason about organization context, effectively re-deriving Rule 11's tenant-isolation work a second time for a concept that did not exist when that work was done — a system-wide re-architecture the initiative's own instructions ("do not rewrite existing architecture," "maintain backward compatibility") explicitly rule out.
- **M:N `organization_workspaces` link table** instead of a nullable FK. Rejected: a workspace in two organizations at once leaves "which org's SSO config / billing plan applies" structurally ambiguous, with no clean resolution rule — the 1:N model sidesteps a problem this platform has no product requirement to solve.
- **A combined `AuthContext` merging workspace and organization role into one object.** Rejected: collapses two genuinely independent authorization questions into one type, the same reasoning ADR-0004 used to reject a combined `get_current_workspace_with_role` dependency — a route that only needs one of the two would have no clean way to depend on just that one.
